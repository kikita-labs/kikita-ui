## State, accessibility, and source behavior

`exclusive` toggles to one ID or no IDs; opening a second item replaces the first. `multi` adds an ID and removes it when toggled again. A consumer can control the model directly. Source does not sanitize externally assigned IDs: an array containing multiple IDs can open multiple panels in exclusive mode, and a disabled item can still be open if its ID is supplied. The page demonstrates normal exclusive and multi transitions and does not present those externally forced combinations as normal behavior.

Each trigger is a native button with `aria-expanded` and `aria-controls`. Its body stays in the DOM as a `role="region"` linked by `aria-labelledby`; a closed body also has `aria-hidden="true"` and `inert`, removed when open. The E2E spec checks those links and closed/open attributes. The chevron is hidden from assistive technology. Accordion does not generate a heading element; the header is string content inside its button.

No custom keyboard handler or roving tabindex is implemented. Enter and Space activation come from native button behavior; Arrow, Home, and End navigation are not implemented. The E2E spec exercises both Enter and Space, keyboard Tab order around a disabled item, and a real `:focus-visible` state. A real assistive-technology review has not been performed.

The stylesheet defines hover, focus-visible, disabled, expanded-chevron, open/closed body transitions, and `prefers-reduced-motion: reduce`. It styles default horizontal dividers, bordered cards, and ghost/no-border treatment. `sm` uses the compact trigger/body rules, `lg` increases trigger height and body spacing, and `md` uses the base styling. Theme and density come from the app shell; the page adds no visual overrides or fabricated Accordion states.

## Limitations and source discrepancies

- Duplicate explicit item IDs are not validated and can duplicate ARIA IDs and share state. All catalogue and interaction examples use unique IDs.
- Auto IDs come from a module-level counter. The spec checks their relationships without relying on literal values, but server/client stability across repeated SSR requests has not been verified; parent verification should watch for hydration warnings.
- An item outside an Accordion has no provider for its internal context. The page keeps every item inside a container.
- `docs/accordion.md` describes the size default as `md`, but source allows the root `KikitaUiDefaults.size` value before falling back to `md`; it also does not enumerate `xs` or explain that `xs` has no Accordion-specific styling.
- The docs mention the trigger/body ARIA links but do not describe closed-state `aria-hidden`/`inert` or keyboard behavior. The page inventory follows implementation and tests for those details.
- The project accessibility guidance requires 44×44px touch targets on touch viewports. The base (`xs`/`md`) trigger uses a 44px minimum height and `lg` uses 52px, but the shipped `sm` trigger is 36px. This is an inherited component sizing limitation: the page records it without changing the existing visuals or claiming the `sm` target meets touch guidance.
- The library unit test verifies open/close, disabled behavior, core ARIA references, and model changes. It does not cover appearance/size styling, root-size inheritance for Accordion, icon projection, generated IDs, native keyboard activation, closed `aria-hidden`/`inert`, duplicate IDs, or SSR/hydration.
- Accordion has no density, shape, loading, selected, validation, or form API; these are intentionally omitted rather than represented by page-only styling.
- Route registration and `provideTranslocoScope('accordion')` are parent-owned and are present in the current Surfaces route fragment. English and Russian scope catalogues are present in `public/i18n/accordion/` with matching key paths.
