## Public contract and example map

`KuiIcon` is exported from the `@kikita-labs/ui` root barrel. The Playground app calls `provideKikitaUi({ scrollbars: 'styled' })`; it does not set an Icon size default, and that root default mechanism does not apply to `kui-icon` because its size accepts raw CSS values rather than `KuiSize` presets.

## Approved page implementation

- The route component is `icon.ts` with the catalogue template in `icon.html`; it uses existing Playground cards, shell theme controls, spacing tokens, and responsive layout patterns.
- The first example is intentionally minimal: `<kui-icon name="kikita-brand" />` with no `size` or `label`. This keeps the visible default local; the page E2E asserts the server markup and hydrated output.
- Local example components cover the seven presets plus numeric/CSS-string sizes, a registered local brand name/direct static SVG/local image URL/projected SVG sources, and decorative versus labeled accessibility output.
- The direct-source and projected SVG examples reuse the exact shipped `kikita-brand` SVG markup; no new glyph art is introduced. The direct source is static and trusted, uses `currentColor`, and is shown alone. It is not combined with `name`; the documented resolver-side effect remains recorded and no library change was authorized.
- EN and RU resources live in `public/i18n/icon/en.json` and `ru.json`. The Data Identity route, `icon` scope, and shared SSR/adaptive registry entry are integrated in the working tree.
- The deterministic E2E spec has no network route stubs. It checks server markup for the local labeled brand SVG, checks every named Icon in the page catalogue uses `kikita-brand` and the only `<img>` uses local `/favicon.ico`, and collects console/page errors around reload/hydration. A shell language-control interaction confirms client behavior after reload. Seven Icon tests pass, covering default, sizes, sources, accessible names, both shell themes, and 320px layout. The generated baselines were visually inspected.
- The page spec does not change or own Data Identity route fragments, shared route/i18n registration, or the shared SSR/adaptive registry. Local-first resolution is established by provider order and newest-first lookup in source; page SSR/hydration assertions passed. The shared Playground header uses `sun`/`moon` through the default Lucide resolver; the page spec does not assert network isolation for shell-owned icons.

## Render, accessibility, and lifecycle behavior

The template selects a truthy resolved SVG first, then a truthy `src`, then projected light-DOM children. The implementation does not gate projection on whether `name`, `source`, or `src` were provided, so projected children also appear while a name is unresolved or after it fails; the component JSDoc only describes projection when all three inputs are unset. Raw projected SVG content is sized to the host. An unregistered/failed name with no image or children has no visible fallback or status indicator. `src` remains available while a name has no SVG result and is replaced if that name resolves. An empty `source` is non-nullish and therefore shadows the resolved name, but is falsy to the template; rendering falls through to `src` or projected content instead of showing that name. These fallback transitions are not unit-tested.

The host is an `inline-grid` sized from `--kui-icon-size` (default `1em`), centers its contents, allows flex/grid shrink with zero minimum sizes, inherits `color`, and aligns to text with `vertical-align: -0.125em`. Resolved and projected SVGs fill the host box; the external `<img>` also fills it. There is no Icon-owned hover, focus ring, animation, or reduced-motion behavior. The library's Lucide and Kikita brand SVGs use `currentColor`; arbitrary consumer SVGs control their own fill and stroke.

Unlabeled icons are decorative and hidden from the accessibility tree. A truthy `label` exposes the host as one image with that accessible name. External images always use empty `alt`. The component is not keyboard-interactive and does not implement keyboard handling. Do not label a wrapping control through the icon input; the actual button/link should own its accessible name.

There is no direct `window` or `document` access in the component. Name resolution uses Angular `resource`; the default Lucide resolver calls global `fetch` and has no browser-platform guard, while the built-in brand icon is local. The source alone and projected content render synchronously. A `name` starts resolution even when `source` is also set. The icon unit specs and shared SSR/hydration E2E spec do not verify Icon server rendering, hydration, or CDN behavior during SSR. The page E2E passed its local server-rendered markup and post-hydration assertions for the page-owned examples; it does not measure shell-owned CDN activity.

## Documentation discrepancies and omissions

- `docs/icon.md` says `source` takes precedence over `name` and causes no registry lookup/network request. Rendering precedence is true, but `resolvedIcon` still receives every non-empty `name` as a resource parameter before `svgSource` selects `source`; a combined instance can invoke its resolver. The current unit test called “before registry lookup” uses a source-only example and never asserts that no resolver runs.
- `docs/icon.md` suggests putting `provideKuiIcons()` in a component `providers` array. Its return type is `EnvironmentProviders` from `makeEnvironmentProviders()`, which Angular reserves for application or route environment injectors; Angular's [EnvironmentProviders](https://angular.dev/api/core/EnvironmentProviders) and [Component API](https://angular.dev/api/core/Component) distinguish these from component `Provider[]`. The page should not rely on that component-level recipe.
- The documented `--kui-icon-size-*` names are consumed with fallbacks in `KuiIcon`, but the [theme generator](../../../../../../../../ui/src/lib/theme/create-kui-theme.ts) has no generated definitions for them. The preset fallback values are implemented in the component; consumers can override those custom properties, but they are not emitted as generated theme tokens. There is no standalone global Icon stylesheet in the [public style entrypoint](../../../../../../../../ui/src/styles/kikita-ui.css); the host rules live in the component stylesheet.
- The component JSDoc says projected content is used only when all three source inputs are unset. The template's final branch projects content any time the SVG and image branches do not render, including unresolved names. This broader fallback is not documented or tested.
- The docs present examples rather than a complete API table and do not list the public `KUI_ICONS` token or all exported helper types. The component has no outputs, methods, keyboard behavior, interactive states, or form contract; none should be invented for the page.
- The library tests do not cover empty labels/empty SVGs, source-plus-name resolver side effects, resolver rejection, pending/resolved `src` fallback transitions, projected-content fallback for an unresolved name, inherited color, or theme rendering. The page SSR/browser assertions passed for the page-owned local examples and do not cover those omitted library edge cases.
