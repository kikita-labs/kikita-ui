## Public API and page coverage

The public import is `@kikita-labs/ui`. `KuiChipDirective`, `KuiChipRemoveDirective`, `KuiChipAppearance`, and `KuiChipSize` are exported from the local component barrel and the public component barrel. Chip has no model inputs or consumer-facing methods.

`button[kuiChipRemove]` is a public behavior-only directive with no own input/output. It applies the remove class and `type="button"`, mirrors the parent Chip disabled state into ARIA/native attributes, and forwards an enabled click to `removed`. The page demonstrates both its plain native button and the documented `kuiIconButton` composition. The two removal approaches are separate examples and are never combined on one Chip.

## Visual states, semantics, and composition

- The default is a visible minimally configured `<span kuiChip>` with neutral appearance, effective `md` size, and no remove child.
- The full appearance × size matrix includes all 24 supported pairs. The shell owns the active theme; the page does not override Chip variables or reproduce Chip styling.
- `chip.css` styles hover, active, and `:focus-visible` for native button/anchor hosts. The remove button has separate hover and focus-visible styling, with no separate active rule. The E2E spec reaches host hover/active/focus and remove-button hover/focus through real pointer or keyboard input; remove hover also asserts that the computed color reaches the hover token. Static spans remain noninteractive; the page does not apply internal `.kui-chip--hover`, `--active`, or `--focus` classes to simulate states.
- The disabled and invalid examples cover the public state inputs. Chip has no selected, loading, or form state. It owns no Delete/Backspace behavior; Select owns selected-value keyboard removal.
- Composition uses the shipped `.kui-chip-icon`, `.kui-chip-avatar`, and `.kui-chip-label` styling hooks, plus the public Avatar component. Projected content remains consumer-owned; these are not Chip inputs or content directives. The long-label example caps only its own host at `max-inline-size: min(100%, 16rem)`, a page-local consumer constraint rather than a Chip input or library style. Desktop and 320px E2E checks confirm that the visible label box clips its contents with the shipped ellipsis while the document has no horizontal overflow.
- Static spans do not acquire an interactive role. Interactive examples use native `button` and `a` hosts. The page gives the action button a page-owned activation count and the link a real in-page target; neither behavior is a Chip output.
- Chip has no shape or density input. Its radius, dimensions, spacing, typography, focus, remove, and appearance colors are CSS variables, including `--kui-chip-radius`, `--kui-chip-height-*`, `--kui-chip-gap-*`, `--kui-chip-font-size-*`, `--kui-chip-disabled-opacity`, `--kui-chip-focus-ring-width`, and `--kui-chip-remove-*`. Appearance CSS maps the semantic color tokens. The page inherits the shell theme and does not fabricate shape/density variants or override token values.
- The stylesheet also contains `.kui-chip-counter`, but Chip exports no counter directive/type and `docs/chip.md` does not document that class. The legacy state row and legacy Playground page use it. Parent review approved omitting this undocumented hook. Select's `+N` overflow is rendered as an ordinary `[kuiChip]`, so the new page does not use `.kui-chip-counter`.

## Accessibility, lifecycle, tests, and discrepancies

The default generated remove button uses a hidden SVG and a value-specific accessible name. Custom remove buttons use native button semantics and their own accessible names. Chip itself does not generate an ARIA role. `disabled` and `invalid` remain distinct: disabled is announced on the host and remove button; invalid changes styling only. The remove button boxes are 10/12/14/18 CSS pixels for `xs`/`sm`/`md`/`lg`, below the playground's 44×44px touch-target guidance. This page verifies keyboard and pointer behavior but does not claim touch-target compliance. It does not claim form validation or add `aria-invalid` on Chip's behalf.

The generated remove button is direct DOM mutation. The directive checks `isPlatformBrowser` and does not create it on the server, preserving the compiled server template; it creates and synchronizes the button after browser construction. The declarative custom remove control is part of normal template SSR. The E2E spec checks that Chip content is server-rendered, the generated control is absent from server markup, and the control exists and works after hydration. No page code accesses browser globals or mutates the Chip host.

The Chip unit spec verifies explicit size/appearance/invalid reflection, custom remove emission, custom disabled semantics, generated button type/icon/label/emission, generic-label fallback, and generated-button disabled behavior. It does not cover the complete appearance/size matrix, the Chip root-size default, a native button host's disabled attribute, keyboard/pointer pseudo-states, `removable` toggling, label changes after creation, or SSR/hydration. The page E2E adds the visible matrix, real interactive host states, controlled removal, disabled native button, server/client checks, and a runtime scope/language switch that also verifies the generated remove label updates after creation. The page intentionally has no input editor to exercise toggling `removable` off; that directive lifecycle edge remains a library-unit-test gap rather than a component-catalogue scenario.

The source documentation describes size as defaulting to `md`; global `docs/di-defaults.md` explains that omitted `size` inputs inherit root `defaults.size` first. The current app config has no size override, so the visible page default is still `md`. The state coverage row says `/chip` and lists the counter, while the new catalogue route is parent-integrated at `/components/chip`; the counter discrepancy is recorded above. The legacy `/chip` page also uses a static `.kui-chip--focus` class and page-authored avatar styling. This page follows the approved real-interaction requirement and reuses shipped KUI visuals instead. No Chip-specific approved design record appears in `docs/design-provenance.md`; the page changes no Chip visual identity and follows the component-page layout contract.

Shipped Chip styles consume 32 Chip-specific CSS variables from `create-kui-theme.ts`: background/hover, border/width, text, radius, size-specific height/gap/font-size/remove-size, padding, weight, disabled opacity, focus rings, icon/avatar treatments, and remove colors/radius. The catalogue treats these as theme hooks, not editable component inputs.

## Deterministic page and browser evidence

The one-scroll page uses `PlaygroundExampleCard` groups for the minimal default, appearance × size matrix, generated/custom removal, disabled/invalid states, composition, and interactive native hosts. Prose labels, group names, accessible remove names, and status messages live under the `chip` Transloco scope in `public/i18n/chip/en.json` and `ru.json`; the size examples deliberately show canonical API tokens (`xs`, `sm`, `md`, `lg`). Matrix examples are visible together; none are hidden behind tabs or accordions.

The focused E2E spec targets accessible group/button/link names and exercises actual browser events. It covers server rendering and hydration, a runtime switch to the Russian Chip scope, all 24 matrix values, generated removal by pointer, Enter, and Space, custom removal by pointer and keyboard, reset, disabled/invalid semantics, real native activation/navigation, focus-visible, hover, and pressed states. Named desktop (1440×1000) and 320px screenshots are specified for the default, matrix, removal before/after each removal method/focus, generated remove-button hover, states, composition, and interactive host focus/hover/pressed sections. The removal focus captures crop to the custom-remove group so the remove control ring is clear without unrelated reset-button state. The mobile helper collapses the shell categories and checks for document-level horizontal overflow before each capture. The focused Playground build passed, the Chip snapshot-update run passed all 11 tests, and the clean Chip suite passed all 11 tests; every generated baseline was visually reviewed for clipping, overlap, scroll ownership, and readability.
