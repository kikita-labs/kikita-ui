# State Coverage

This is a scenario and evidence register for public Kikita UI primitives.
A listed scenario is not proof of a passing test. Inherited review reports below
lack complete revision/artifact metadata and must not be used as fresh release
certification. Open work is owned by [the roadmap](component-roadmap.md).

## Evidence Records

For new verification, record scope, method/command, date, revision, result, and
artifact (or explain why none exists). Separate source inspection from unit,
browser, visual, SSR/hydration, and assistive-technology evidence.

## Current Gaps

- File Upload does not implement an Angular Signal Forms control contract; `files` is a plain
  two-way `model()`. It has no built-in upload transport -- the consumer owns `status`/`progress`
  on the model past the initial `pending`/`error` produced by picking. DOM accessibility smoke has
  run for `kui-file-upload`; deeper assistive-technology feedback will be handled after release
  if users report concrete issues.

- Initial static accessibility review has been run for Table, Tooltip, Tabs, Segmented, Popover, Dialog, Toast, Accordion, Progress, and Slider. Fixes from that pass include native sortable table header buttons, accessible tab scroll buttons, toast `status`/`alert` live semantics, tooltip whitespace guarding, and Signal Forms native range coverage for Slider.
- Initial browser snapshot review has been run for Table, Select, Dialog, and Popover. Fixes from that pass include Popover trigger initialization guarding for Angular 22 required-input timing.
- Unit coverage verifies that Dialog and Drawer backdrop dismissal is limited to pointer interactions
  that start on the backdrop; Chromium behavior coverage verifies the Dialog flow end to end.
- Initial browser smoke review has been run for Dropdown, Toast, Accordion, Progress, Slider, Number Input, Combobox, Command Palette, and Scrollbar at desktop and narrow mobile widths. A focused Chromium route smoke has also been run for Field, Select, Combobox, Command Palette, and Scrollbar after the scrollbar provider option. Fixes from earlier passes include local horizontal scrolling for the Progress circular matrix, router-navigation tabs without stale `aria-controls`, dynamic Tooltip `aria-describedby` references only while tooltip DOM exists, overlay trigger `aria-controls` references only while Dropdown, Select, Popover, and Combobox panels exist, Combobox clear detaching its CDK overlay, and disabled Chip remove actions using native disabled button semantics.
- Full static component audit has been run across implemented primitives for docs presence, JSDoc coverage, public style entrypoint coverage, tracked Cyrillic leakage, overlay/CDK usage, and obvious SSR DOM access. Fixes from that pass include SSR-safe injected `DOCUMENT` usage for overlay listeners/toast region creation, browser-guarded Slider DOM generation, corrected `kuiInput` scope to native `input` only, and missing import blocks for Dialog, Icon, Popover, and Toast docs.
- Agent documentation, repo-distributed skills, skill synchronization, script tests, Husky hooks, and Playwright SSR/browser gate wiring were added as tracked quality surfaces. The expanded static audit now checks agent/doc links, skill shape, component docs presence, public export JSDoc, public style entrypoint imports, tracked Cyrillic, route coverage, and obvious top-level browser globals.
- Playwright browser smoke now covers representative behavior, DOM accessibility, responsive overflow, committed visual baselines for stable routes, and SSR hydration. The automated accessibility smoke excludes known pre-existing playground/demo-only rule categories for color contrast, token swatch ARIA labels, empty demo table headers, title-only field examples, and Safari scrollable-region focusability; these exclusions do not count as assistive-technology review.
- Manual keyboard/accessibility review has been reported by the maintainer and is accepted for the `1.0.0` go/no-go decision. A formal screen-reader matrix is not a `1.0.0` blocker; concrete user-reported accessibility issues should be fixed in a patch or minor release depending on whether the public API must change.
- Menu submenu, checkbox/radio item, and context-menu helper are deferred per the Claude Design brief and are post-1.0 scope unless a real consumer blocker appears.
- Combobox and Command Palette now use CDK overlay positioning. Committed visual baselines cover representative stable routes; deeper assistive-technology review remains useful, but it is not a `1.0.0` blocker.
- Breadcrumbs ships three CSS-only responsive patterns (truncate, ellipsis, first+last) but does not wire an ellipsis-triggered overflow menu itself; consumers combine `.kui-breadcrumb-ellipsis` with an existing `kui-menu`/`kui-dropdown` per the Claude Design brief's own "explicitly not included" note.
- Date Picker only auto-wires `kui-calendar` (single-date). The design brief's `range` mode (one-field and two-field layouts, two linked calendars) and the mobile bottom-sheet popover variant are post-1.0 scope -- see `docs/date-picker.md` Known Gaps. `kui-calendar-range` exists as a standalone primitive for range selection, but is not yet composed into a popover-based picker.
- `input[kuiDatePicker]`'s auto-wire effects only forward `value`/`viewDate` to a paired `kui-calendar`; `minDate`/`maxDate` still require binding on both elements, since `kui-calendar` declares them as plain (non-model) inputs with no supported way to override from a `contentChild` reference -- see `docs/date-picker.md` Disabled Dates.
- Calendar/Calendar Range multiple selection mode, Tree custom icon templates/virtualization, and File Upload Signal Forms integration are also post-1.0 scope. The current docs describe the shipped behavior and do not promise those capabilities.
- `kui-dropdown` gained a viewport-clamped `max-height` (always `min(maxHeight, calc(100vh - margin))`) and closes itself when its anchor scrolls out of the viewport. Browser-verified for Date Picker; not yet re-verified with committed screenshots for Select/Combobox/Menu.
- `input[kuiNumberInput]` keeps its native input unwrapped during server rendering so Angular hydration can match the template DOM. The browser enhances the input with the `.kui-number-input` wrapper and step buttons after hydration. This preserves the directive API while avoiding the 0.4.4 duplicate-wrapper mismatch.
- Alert (`kui-alert`) is a controlled component: it never removes itself from the DOM. `(closed)` only notifies the consumer, the same pattern `[kuiChip]`'s `(removed)` uses -- the playground demo tracks dismissed state itself, mirroring the Claude Design mockup. `title` is intentionally optional (unlike Toast, where it is required) per Claude Design spec `01 Alert.dc.html`'s open questions. `/alert` has been reviewed in the browser at desktop width in both light and dark theme with no console errors; committed visual regression baselines and a formal assistive-technology review are not yet run.
- OTP Input (`kui-otp-input`) is a new composite component (not a directive on a native element) because it needs roving keyboard navigation, paste distribution, and coordinated per-cell value state across cells -- each cell still renders the kit's own `input[kuiInput]` unmodified. It has no built-in success/error status icon after verification (it cannot know a server verification result on its own); `loading` disables every cell, blurs the entered code in place, and shows a centered `Loader` without changing the group's size -- an intentional scope/design decision documented in `docs/otp-input.md` and the Claude Design spec notes, not a gap. `value`'s join-based semantics collapse a cleared middle cell's position, matching the Claude Design spec's own reference behavior. Unlike `kui-segmented`, the first cell adopts the ancestor `kui-field`'s `controlId`, so `kui-field`'s `label[for]` correctly focuses it (verified in a real browser -- jsdom does not implement label-activation behavior); `hint`/`error` reach the group via `aria-describedby`, and an ambient `kui-field` `error` (with no `[formField]`) alone already marks the cells invalid, the same as a plain `input[kuiInput]`. `/otp-input` has been reviewed in the browser at desktop width and narrow mobile width in both light and dark theme with no console errors; committed visual regression baselines and a formal assistive-technology review are not yet run.
- Pagination (`kui-pagination`) is a composite component (not a directive) that only owns the page-window/ellipsis algorithm (ported from MUI Pagination's `usePagination`) and coordinated `currentPage`/`pageSize` state -- every visible control reuses `button[kuiButton]`, `button[kuiIconButton]`, and `input[kuiSelect]` unmodified except a per-size `min-inline-size` override on page-number buttons for a uniform square footprint. It is deliberately a plain sibling of `table[kuiTable]`, never nested inside it: `kuiTable` is a directive on a bare `<table>` (whose only legal children are thead/tbody/tfoot/tr), holds/sorts the full dataset, and has no pagination/slicing concept of its own, so the consuming page owns `currentPage`/`pageSize` and derives the table's page slice -- the same external composition Angular Material uses for `mat-paginator` + `mat-table`/`DataSource`, not PrimeNG's `p-table`-owns-its-paginator pattern, which only works because `p-table` is a wrapping component rather than a directive over a native `<table>`. No DI token bridges the two components. Not a `FormValueControl` -- pagination is page-level navigation state, not a form field value, so it never goes inside `kui-field`. The current page is marked with `shape="solid" appearance="primary"` plus `aria-current="page"` (state never carried by color alone), matching Claude Design spec `03 Pagination.dc.html` exactly. First/Prev/Next/Last are this component's own internal chrome, not user-facing content, so they render as static inline SVG from `kui-chrome-icon-paths.util` (the same pattern `kui-select`'s dropdown chevron and `kui-tabs`' scroll chevrons use) instead of `IconButton`'s network-dependent, name-resolved `icon` input -- avoiding a CDN dependency for core keyboard/mouse navigation chrome. `/pagination` has been reviewed in the browser at desktop width in both light and dark theme with no console errors, and is covered by the automated document-overflow check at 320/390/768/1440px; committed visual regression baselines and a formal assistive-technology review are not yet run.
- Time Picker (`input[kuiTimePicker]` + `kui-time-picker-panel`) follows the exact composition of `kuiDatePicker`/`kui-calendar`: the directive auto-wires a sibling panel found inside the same `kui-field` (`value` both ways, `format`/`hourStep`/`minuteStep`/`secondStep`/`showSeconds`/`minTime`/`maxTime`/`disabledHours`/`disabledMinutes`/`disabledSeconds` push-only). The panel is also usable inline/standalone on its own, like `kui-calendar` -- its ancestor `kui-dropdown` injection is optional, and it auto-detects whether one is present to decide its own chrome (`data-kui-flat` drops its background/border when nested in a dropdown that already draws one, kept when standalone). Per Claude Design spec `04 Time Picker.dc.html`'s own open questions: the leading clock icon (`KUI_CLOCK_CIRCLE`/`KUI_CLOCK_D`) is a new static chrome glyph added to `kui-chrome-icon-paths.util`, not routed through the async `kui-icon` registry -- same treatment as `KUI_CALENDAR_D`; typed text auto-inserts the `:` separator as digits are typed (beyond the design spec's own reference, which only filters characters) and strips characters that could never be part of a valid value, but final parsing is still a simplified locale-less regex match, same strategy as the date picker's `dd.MM.yyyy`, and caret position is not preserved across a rebuild; every column centers on its selected cell both when the panel opens and on every later selection (click/keyboard/"Now", including a field changed only as a side effect of another one) -- superseding the design spec's own reference, which ruled out auto-scroll-on-open because its `centerColumn` used `scrollIntoView` (which would also drag the dropdown panel and the host page along); this component's own `scrollTop`-rect-math centering is scoped to the individual column, so that problem doesn't apply and the open-state scroll gap was closed. The open-time center reacts to the ancestor `kui-dropdown`'s own `isOpen` signal, not this component's construction -- manual browser testing found a given `kui-dropdown` instance's content can either get recreated fresh on every open or reused across opens (observed both from different dropdown instances on the same page), so centering on construction alone missed every open of a reused instance; reacting to `isOpen` is correct either way; cells are fixed squares (`inline-size == block-size == --kui-control-height-sm`) rather than flex-stretched, so a scrolling column's cells stay the same size as a non-scrolling column's without reserving dead scrollbar-gutter space in columns that never scroll; selecting a column cell deliberately does not auto-close the panel (picking hours would otherwise close it before minutes/seconds); an unset value used to fall back to the real current time for any field the user hadn't touched yet (e.g. picking only a minute would silently pick up the real current hour) -- the fallback base is now a fixed local midnight; range mode is not implemented. Verified in a real browser via Playwright (desktop, dark theme): centering, cell-size parity, colon auto-insertion, the midnight-base fix, and the Signal Forms error message rendering through `kui-field`; committed visual regression baselines and a formal assistive-technology review are not yet run.
- Link (`a[kuiLink]`/`button[kuiLink]`) composes `[kuiText]` via Angular's Directive Composition API (`hostDirectives`), exposing only `variant`; `[kuiText]`'s own `tone` is not exposed, so `[kuiLink]`'s `tone` is the only color input in its public API, never coinciding with a same-named input on a separately-applied directive. Verified with `/link` added to the Playwright `a11y` (axe, 0 violations) and `responsive` (320/390/768/1440px, no document overflow) suites; adding the route to `responsive` surfaced a real playground-page bug -- `.tone-row`'s fixed-width label + link combo defaulted to `min-width: auto` as a `.component-board` grid item and refused to shrink below its own content width at 320px, overflowing the `minmax(0, 1fr)` track `.component-board` relies on to constrain wide rows (same failure mode its own code comment warns about) -- fixed with `min-width: 0` plus `flex-wrap: wrap` on `.tone-row`. Unit-tested (10 specs): tone/underline host attributes, `variant` forwarding to the composed `[kuiText]`, disabled anchor/button conventions, external auto-detection (rel merge, static chrome icon, hidden a11y hint), explicit `iconEnd` overriding the auto chrome icon, `iconStart` insertion, and no DOM mutation on the server platform. Not yet run: committed visual regression baselines and a formal assistive-technology review (same gap every other primitive in this table currently has).
- Media Viewer (`kuiMediaViewer()` + internal `kui-media-viewer`) is a new pattern: an imperative opener over `KuiDialogService`, the same shape as `kuiDialog()`/`kuiConfirm()`/`kuiDrawer()`, built from Claude Design spec `06 Media Viewer.dc.html`. `KuiDialogSize` gained a `'fullscreen'` value (width/height 100vw/100vh, no radius/border/shadow/padding) so the lightbox panel fills the viewport through the dialog's own size preset instead of a page-level CSS override reaching into `.kui-dialog` from outside -- the spec's own open question #2 flagged exactly this as the correct fix if the fullscreen pattern were needed beyond this one component. Close/Prev/Next/Zoom in/Zoom out are `button[kuiIconButton]` (`shape="ghost"`) with static inline SVG content instead of the network-dependent, name-resolved `icon` input, the same treatment `kui-pagination`'s First/Prev/Next/Last already get (`KUI_ZOOM_LINE_H_D`/`KUI_ZOOM_LINE_V_D` were added to `kui-chrome-icon-paths.util`, reusing the existing search-icon circle/handle shape for zoom in/out, matching Lucide's own glyphs). Per the spec's own open questions: pan while zoomed uses a fixed offset budget per zoom step (`120px * (zoom - 1)`), not a measurement of the photo's actual rendered size. Grid layout, per-tile multi-select (a consumer-owned `input[kuiCheckbox]` next to the cover button), and any trigger element are the consumer's own composition around the opener, not part of its API -- it only ever renders the fullscreen lightbox. Video is out of scope (photos only), per the spec's own form of clarifications. Pan/zoom pointer handling was revised after initial delivery based on real-browser testing: the photo pan drag now calls `setPointerCapture` on pointerdown (guarded with `?.` for environments without it) so pointerup/cancel are always delivered even if the pointer is released outside the browser window, and the drag stops the instant the pointer leaves the whole lightbox -- checked against the viewer's own bounding rect, not the (much smaller) photo frame, so a drag that crosses the frame's edge near the end of a gesture doesn't cut off early. `draggable="false"` plus `user-select: none` on the photo, and `user-select: none` on the whole `.kui-media-viewer` root (the same treatment `button[kuiIconButton]` already applies to itself), stop a pan drag from ever turning into the browser's own "drag this image out" or text-selection gesture -- including when `event.preventDefault()` on pointerdown wasn't enough by itself, e.g. dragging over content selected elsewhere on the page via Ctrl+A. Wheel/trackpad zoom (one `zoomStep` per wheel event, scroll up zooms in; a trackpad pinch arrives as `ctrlKey` + wheel, handled the same way) and continuous touchscreen two-finger pinch-zoom (tracked via multiple concurrent pointer ids, scaling from the finger distance and zoom level at pinch start) were added as new interactions, not part of the original Claude Design spec. Unit-tested (15 specs): initial-index clamping, `onIndexChange` on open and navigation, Previous/Next boundary disabling, non-looping Left/Right/Home/End keyboard navigation, Close routing through the dialog context, zoom in/out bounds with pan reset at 1x, wheel zoom in/out, pointer-drag pan clamped to the pan limit, pan stopping once the pointer leaves the viewer bounds, two-pointer pinch-zoom, per-photo `Skeleton`-then-reveal and `EmptyState`-on-error stage states, the thumbnail strip hiding for a single-photo gallery, and thumbnail-click navigation; plus a `KuiDialogContainerComponent` spec covering the new `fullscreen` size class. `/media-viewer` has been manually reviewed in a real browser (desktop, dark theme) by the maintainer, who reported and confirmed the fixes for the button-jumps-on-press, native-image-drag, and text-selection issues above, plus three narrow- mobile-only bugs found the same way: the thumbnail strip pushed the page wider than the viewport instead of scrolling internally (a flex item's default `min-inline-size: auto` floors it at its content width regardless of the parent -- the same fix already applied to `button.css`/ `chip.css`/`otp-input.css`, just missed here), a real two-finger touch pinch could be hijacked by the browser's native page pinch-zoom because `touch-action: none` was set on the photo `<img>` only, not the `.kui-media-viewer__frame`/`.kui-media-viewer__stage` elements a second finger can easily land on, and -- caught by manually scrolling `.kui-media-viewer__strip` to `scrollLeft: 0` and checking the first thumbnail's own bounding rect, not just eyeballing a screenshot -- `justify-content: center` on an overflowing flex row left the first (and, symmetrically, part of the last) thumbnail permanently unreachable by scroll, fixed with `justify-content: safe center` falling back to start-alignment specifically when centering would strand overflow content. `KuiMediaViewerItem.id` is now optional, defaulting to `src` (a URL is already a natural stable key for a photo, the same "prefer a stable field already in your data over a generated one" guidance Angular's own `trackBy` docs and React's key-prop guidance both give) rather than requiring every consumer to invent one; `@for` loops use `$index` directly instead of aliasing it through an unnecessary `let i = $index` (the alias exists for nested-loop name collisions, not present here). A single photo (`items.length === 1`) needs no separate single-photo API: the counter, Prev/Next, and thumbnail strip render only for `items.length > 1`, the same "one gallery API that degrades gracefully" approach established lightbox libraries (PhotoSwipe, yet-another- react-lightbox) take, rather than a second component for what is a subset of the same behavior. Committed visual regression baselines and a formal assistive-technology review are not yet run.
